# 图片到 UMG：先判定集合，再生成节点

## 输入与边界
- 输入：截图、画布尺寸；可选的界面用途、用户指定的动态集合。
- 一张截图不能证明数量是否动态、是否滚动或是否需要虚拟化。区分截图可见事实、合理推测与用户确认；不虚构运行时行为。
- 本项目只生成静态视觉包，不生成数据绑定或业务逻辑。
- 先阅读项目 README.md、src/core/types.ts 和 examples/input.visual.json。不要直接臆造最终 UMG JSON。

## 第一步：集合候选清单（必须先做）
扫描整个画面，而非只找三个一模一样的框。为每个候选记录：区域、单条目的边界、可见数量、重复字段、排列方向、支持证据、反证、决策与待确认项。

判断顺序：
1. **条目语义**：是否是同一种实体的多条记录（任务、商品、背包道具、联系人、排行榜行）？还是各自承担固定职责的控件？
2. **条目边界**：一个条目包含哪些图标、文字、按钮、背景？先把一个完整条目归到一个容器，不能把每条记录里的图标列和文字列分别当列表。
3. **共享模板**：变化的是文本/图片/颜色/进度等数据，还是结构和布局本身？选中态不等于另一种条目。缺少徽章等异构情况必须明确记录，不凭空补造可见元素。
4. **布局**：单行或单列选 list；多行多列且规则排布选 tile。看到格子不等于必须 TileView，固定功能格子可以是普通布局。
5. **不确定性**：仅看到两项不能排除列表；只有一项、裁切严重或用途不明时，保留普通布局并询问关键问题。不因为“看起来整齐”就宣称需要列表。

典型正例：两条明确的任务记录 → list；规则排列的商品卡片 → tile；横向展示同类玩家 → list。
典型反例：确认/取消/返回按钮、顶部导航、姓名/等级/战力属性栏、固定装备部位、装饰圆点 → 通常 none，除非用户明确要求集合实现。

## 第二步：显式组织 VisualNode
- 所有 bounds 都是相对整张画布的绝对坐标，不是相对父节点。
- 每个集合建立独立 Canvas 容器，直接 children 只放完整条目。标题、过滤栏、滚动条、分页按钮与集合容器平级，不混入条目。
- 容器顶层字段 collection 使用：list / tile / none / auto。不要放进 props。
- 已明确集合用 list 或 tile；固定布局及不确定区域用 none；auto 仅用于有意保留旧几何启发式的区域。
- none 仅阻止本层直接子节点合并，嵌套容器仍独立判定。逐层检查，尤其条目内部的并排文字或按钮。
- 显式 list/tile 至少需要两项，且仍需通过同构及几何校验；标注不是强制忽略不一致。
- 条目子树顺序、节点类型、对应字段集合保持一致；允许字段值不同。节点 id 在整棵输入树中保持唯一。
- 不支持的异构条目、可变高度或裁切条目应保留并说明限制，不伪造规则数据以强行通过检查。
- 只有一行的网格截图，不能从几何证明多行 TileView；若用户需要网格语义，记录需求，说明当前提取器限制。

## 第三步：生成、检查、纠错
运行：
```bash
npm run extract -- <input.visual.json> <output-directory>
```
检查 stderr 的每条 extracted/skipped 诊断，并对照候选清单：
- 所有确定的集合是否产生了预期 ListView/TileView？
- 固定按钮、标题、条目内部字段是否被误提取？
- preview 项数是否等于可见完整条目数，阅读顺序是否正确？
- 末行不满的网格是否从第一列开始且列对齐？
- entry 是否保留了完整条目，文本、图片和状态差异是否进入 overrides？

若 skipped，先修正条目分组、坐标或结构；不能靠反复降低容差、复制条目或删除异常项掩盖问题。无法安全转换时保留普通节点并报告原因。
生成成功只代表结构校验通过，不代表截图还原准确。还需在预览中对照原图检查边界、间距、缺失元素与状态。不能声称已运行未实际执行的预览/UE 检查。

## 交付
给出输入 JSON、生成包、集合决策摘要、未解决问题与验证记录。用户纠正的集合判断优先于视觉猜测，并固化到 collection 标注，而不是只记在对话里。
